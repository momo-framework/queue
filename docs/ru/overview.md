# Обзор

`momo/queue` — слой отложенной работы в Momo. Он нужен, чтобы чувствительные к
задержке обработчики запросов (оформление заказа, корзина, колбэки платежей)
выгружали медленную или ненадёжную работу — отправку писем, вызовы платёжного
шлюза, переиндексацию — в фоновый воркер, а не блокировали ответ на горячем пути
45k+ RPS.

## Место в системе

```
HTTP / Command handler ──push()──▶ QueueInterface ──pop()──▶ Worker ──▶ handle()
                                          │                     │
                                     (кучи приоритета       при ошибке
                                      и задержки)           └─ release() с backoff
                                                            └─ FailedJobStore + JobFailed
```

Пакет зависит только от `momo/kernel` (база service provider), `momo/console`
(команды воркера) и `momo/events` (события жизненного цикла). Он не тянет напрямую
ни базу данных, ни Swoole: учитывающее корутины ожидание простоя изолировано за
`SleeperInterface`, что делает движок тестируемым и чистым по слоям.

## Основные строительные блоки

| Концепция           | Тип                            | Ответственность                                  |
|---------------------|--------------------------------|--------------------------------------------------|
| Задача              | `JobInterface` / `AbstractJob` | единица работы + лимит попыток + хук `failed()`   |
| Конверт             | `Envelope`                     | неизменяемая обёртка: id, приоритет, доступность, попытки |
| Очередь             | `QueueInterface` / `InMemoryQueue` | хранилище с порядком по приоритету и задержке |
| Куча                | `PriorityQueue`                | бинарная куча; PHP-fallback для нативной min-heap |
| Backoff             | `BackoffPolicyInterface`       | стратегия задержки повторов (экспон./константа/jitter) |
| Воркер              | `WorkerInterface` / `Worker`   | разгребает очередь, повторяет, отправляет в dead-letter |
| Хранилище упавших   | `FailedJobStoreInterface`      | записи dead-letter для исчерпавших попытки задач  |

## Проектные решения

- **Две кучи, а не одна.** Готовые задачи упорядочены по приоритету; отложенные —
  по времени доступности. `pop()` переносит наступившие отложенные в готовую кучу
  и извлекает. Это сохраняет и «сначала наивысший приоритет», и «не раньше срока»
  без сканирования.
- **Инъекция часов.** Любое чтение времени идёт через `ClockInterface`, поэтому
  поведение задержки и backoff детерминируемо в тестах (`MutableClock`).
- **Неизменяемые конверты.** Обработка повторов пересобирает конверт с
  увеличенным числом попыток, а не мутирует общее состояние — безопасно между
  корутинами.
- **Backoff как стратегия.** Задача может переопределить дефолт воркера, реализовав
  `HasBackoffPolicyInterface`.

## Память и корутино-безопасность

`InMemoryQueue` и `InMemoryFailedJobStore` хранят состояние на время жизни
воркера, не на запрос, поэтому межзапросного накопления нет. Их мутирующие методы
не содержат точки приостановки I/O, поэтому при кооперативном планировщике Swoole
они атомарны относительно соседних корутин в том же воркере. `Worker` соблюдает
лимит памяти (`WorkerOptions::$memoryLimitMb`) и чисто завершается при его
превышении, позволяя runtime-guardian'у поднять свежий воркер — точка передачи
back-pressure против медленных утечек.

Для межворкерного распределения свяжите реализацию `QueueInterface` на базе Redis
или БД — контракты для этого спроектированы.
